## 0b. 为什么不需要"数据库服务"(回答你的猜测)

| 方案 | 费用 | 运维 | 并发能力 | 结论 |
|---|---|---|---|---|
| **A. SQLite(node:sqlite 内置)** | 0 | 零(单文件,随应用备份) | 低并发读写完全够(几十~几百用户) | ✅ **推荐** |
| B. 腾讯云托管 MySQL | ~50~100 元/月起 | 低 | 高 | ❌ 过度设计 |
| C. 自建 PostgreSQL(Docker) | 0 | 中(容器/升级/备份) | 中高 | ⚠️ 备选,当前没必要 |

选 A 的依据:单机 2核4G、目标流量是"面试演示 + 小范围使用"、`node:sqlite` 是 Node 22.5+/24 内置模块(本地 22.23 与服务器 24 均已验证可用)、同步 API 与现有代码风格完全一致、未来要扩到 PG 时 SQL 语句可直接迁移。

## 1. 总体框架

```
浏览器
  │ HTTPS(域名阶段) / HTTP(IP 阶段)
  ▼
Nginx(域名阶段) → Next.js API(13 个路由)
  │  ① 认证层(已有,复用):scrypt 密码 + HMAC 会话 token → 解析出 username
  │  ② 授权层(已有,复用):requireAuth 全部 API 已接;本次新增"行级隔离"
  ▼
数据层(本次改造):lib/store.js → node:sqlite
  │  所有 SQL 强制 WHERE user_id = 当前会话用户
  ▼
/opt/star-map/data/star.db(WAL 模式,每日 03:30 备份,保留 7 份)
```

### 核心隔离原则(不串号 / 不越权的根基)

1. **userId 永远来自会话**,不来自客户端:API 不接收任何 userId/username 参数,全部从签名会话 token 解析;
2. **所有数据行带 `user_id` 列**,所有读写 `WHERE user_id = ?`;
3. 用户 A 用自己会话访问用户 B 的资源(sessionId/topicId/date)→ 查无此记录 → 404/403,而非返回数据;
4. 数据对象(画像/主题/报告)在引擎层仍是纯对象,引擎代码(engine/behavior/intent/colors/period/prompts)**零改动**。

## 2. 数据模型(SQL)

```sql
-- 用户(认证 + 轻量信息)
CREATE TABLE users (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  username      TEXT NOT NULL UNIQUE,          -- 唯一,注册时冲突校验
  password_hash TEXT NOT NULL,                 -- scrypt$salt$hash
  birth_date    TEXT,
  star_sign     TEXT,
  star_symbol   TEXT,
  cohort        TEXT,                          -- JSON(代际特征对象)
  career_stage  TEXT DEFAULT '',
  persona_tier  TEXT DEFAULT 'logical',
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);

-- 画像(每用户一行;大 JSON 整存,引擎层零改动)
CREATE TABLE profiles (
  user_id        INTEGER PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  topics         TEXT NOT NULL DEFAULT '[]',   -- JSON
  edges          TEXT NOT NULL DEFAULT '[]',
  feedback_log   TEXT NOT NULL DEFAULT '[]',
  emotion_series TEXT NOT NULL DEFAULT '[]',
  reports        TEXT NOT NULL DEFAULT '{}',
  period_reports TEXT NOT NULL DEFAULT '{}',
  behavior       TEXT,                         -- JSON|null
  last_report    TEXT,                         -- JSON|null
  opener_idx     INTEGER NOT NULL DEFAULT 0,
  last_openers   TEXT NOT NULL DEFAULT '[]',
  adapt_log      TEXT NOT NULL DEFAULT '[]',
  generating     INTEGER NOT NULL DEFAULT 0,   -- 0/1(报告生成中标志)
  updated_at     TEXT NOT NULL
);

-- 日记(UNIQUE(user_id,date) = 一天一条,天然防重复)
CREATE TABLE days (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id   INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  date      TEXT NOT NULL,
  free_text TEXT NOT NULL,
  q1 TEXT DEFAULT '', q2 TEXT DEFAULT '', q3 TEXT DEFAULT '',
  UNIQUE(user_id, date)
);

-- 对话会话(每用户独立 sessionId 空间)
CREATE TABLE chats (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  session_id TEXT NOT NULL,                    -- 客户端可见的会话 id
  source     TEXT NOT NULL,                    -- record|star
  day        TEXT NOT NULL,
  messages   TEXT NOT NULL DEFAULT '[]',       -- JSON
  covered    INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(user_id, session_id)
);

CREATE INDEX idx_days_user_date ON days(user_id, date);
CREATE INDEX idx_chats_user_day  ON chats(user_id, day);
PRAGMA journal_mode = WAL;       -- 读写并发更稳
PRAGMA foreign_keys = ON;        -- 级联删除(注销账号自动清数据)
```

**设计要点**:profiles 的 topics/edges/reports 等保持 JSON 大字段整存,而不是拆成关系表——这样 `engine.js` 内部的对象操作(抽取/归并/报告)**一行都不用改**,只换 store 层的读写实现。等主题数 >100 需要跨用户统计时,再按需要拆表(P1+)。

## 3. 安全设计(在 A 组成果上新增)

| 层 | 已有(复用) | 本次新增 |
|---|---|---|
| 密码 | scrypt 哈希 ✅ | 无 |
| 会话 | HMAC 签名 token(含 username)✅ | 无(无状态,token 里的 username 即身份,不需要 sessions 表) |
| API 鉴权 | 13 路由全接 requireAuth ✅ | 无 |
| CSRF / 输入校验 / 限流 | ✅ | 登录限流加**用户名维度**(同用户名 5 次失败也锁,防定向爆破) |
| **数据隔离** | — | **全表 user_id + WHERE 强制**(§1 三原则) |
| **注册** | 单账号(拒绝已有账号) | **开放注册**:新用户名 → 插 users 行 + 空 profiles 行(事务);用户名冲突 → 409「该昵称已被使用,换一个吧」 |
| 管理员能力 | reset-password.mjs | 仅 SSH 脚本:重置密码(指定用户)/ 删除用户(级联清数据)/ 导出某用户数据 |
| 注销机制 | — | 提供「注销账号」按钮(合规 D 组):二次确认后删除 users 行,级联清空,清 cookie |

**越权测试矩阵(验收必过)**:

1. A 注册 → B 注册同名 → 409;B 注册异名 → 各自独立画像;
2. A 登录后请求 B 的 sessionId 聊天记录 → 查无 → 404;
3. A 提交 B 的 topicId 做合并/拆星 → 404「星星不存在」;
4. 请求体伪造 `userId/username` 字段 → 被忽略(代码不读取);
5. A 的会话 token 直接改成 B 的用户名(篡改签名)→ 401;
6. 未登录访问任何数据 API → 401;
7. A、B 同时并发写各自日记 → 双方数据完整(WAL + 事务);
8. 注销 A → A 的所有行消失,B 数据无影响(外键级联)。

## 5. 数据迁移(上线时执行一次)

1. **备份先行**:`tar -czf /var/backups/star-map/pre-migrate-$(date +%s).tar.gz -C /opt/star-map/data .`
2. 跑 `migrate-to-sqlite.mjs`:读 `data/profile.json + days.json + chats.json` → 建表 → 以「anning」为用户名写入 users/profiles/days/chats(密码需重新设置,旧哈希已弃)
3. 校验:行数核对(users=1、days=7、chats=原会话数)+ 抽样比对画像 JSON
4. 旧 JSON 移入 `data/legacy-json/`(保留观察,不删)
5. 成功后 `reset-password.mjs anning <新密码>`

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| node:sqlite 标记 experimental(22.x 会打警告) | 功能稳定、本地/服务器已验证;备选方案 better-sqlite3(需服务器装 build-essential,已写入手册) |
| SQLite 单写者并发瓶颈 | WAL 模式 + 低流量场景无虞;真到高并发(P3)再迁 PG |
| 迁移失败/数据损坏 | 迁移前备份 + 旧 JSON 保留 + 幂等迁移脚本可重跑 |
| 用户数据合规 | 「注销账号」即物理删除(级联);隐私政策上线(清单 D) |
| 忘记密码滥用重置 | 重置仅 SSH 脚本,不提供自助找回(演示期合理;P2 可加邮箱验证) |
