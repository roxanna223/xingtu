#### 1. Dify — LLM 应用编排平台

- **仓库**：https://github.com/langgenius/dify ｜ **Star** 153,791 ｜ **主语言** TypeScript（后端 Python）｜ **许可证** 修改版 Apache 2.0（Dify Open Source License）｜ **归档** 否，`pushed_at` 2026-08-29（极活跃）
- **定位**：把「Agentic 工作流、RAG 流水线、多模型/多工具」打包成一个协作工作区，云端/私有化/自部署均可。

**核心机制 / 架构**
- 前后端分离：后端 Python（Flask + Celery），前端 Next.js(React)。核心目录：`api/`（REST 接口）、`core/`（编排引擎：agent / workflow / model_runtime / rag）、`web/`（控制台）。
- 五种应用形态：Chatbot、**Agent**、Chatflow、Workflow、Text Generator。
- **Agent 编排**：Agent 节点支持两种推理策略 —— `Function Calling`（结构化工具调用）与 `ReAct`（Thought/Action/Observation 循环）；内置丰富工具（搜索、HTTP、代码执行、知识检索等）并可自定义 API 工具（OpenAPI schema）。
- **知识库 RAG pipeline**：数据集(Dataset) → 分段(segmentation，支持自定义分隔符/正则/代码分块) → 索引(indexing，选 Embedding 模型，Economical/HQ 两档) → 检索(Retrieval，向量检索 + 可选全文/混合检索 + Rerank + top_k 与 score 阈值)。支持 Weaviate/Qdrant/Milvus/PGVector 等多种向量库。
- **Workflow**：节点式 DAG（开始 / LLM / 知识检索 / 问题分类 / 条件分支 / 代码执行 / HTTP 请求 / 迭代 / 参数提取 / 变量聚合 / 模板转换 / 结束），支持聊天流与后台工作流。
- **模型层**：`model_runtime` 抽象 100+ 模型（含 **DeepSeek**，仓库 topics 明确标注 `deepseek`），一套代码切换底层模型。
- **部署**：Docker Compose 一键（api / web / worker / sandbox / db / redis / 向量库等多个容器），偏重。

**与星图的关联点**
- 小星多技能路由：借鉴其「Agent 节点 = 工具列表 + Function Calling 策略」，映射到「小星 = 一个带 测验/目标拆解/个人定位 三类技能的 agent，用 function calling 路由」。
- 自我进化提示词沉淀：借鉴其「应用配置 + 变量 + 数据集」把提示词/上下文做成可版本化管理资源的思想（星图现用 JSON 文件存提示词，可类比 Dify 的"应用/知识库"资源模型，但不必引入整套平台）。
- 6:00 定时日报：Dify 的 Workflow 支持定时触发（cron），但需平台常驻运行；对星图偏重。

**可借鉴资产**（抄思想为主）
- 「工具 + Function Calling 路由」的 agent 封装范式（Python `core/agent`）。
- 知识库三段式 pipeline（分块→索引→检索→rerank）——若未来给「小星」加长期记忆/RAG，直接照此拆模块。
- 技术栈：Python + Celery + React，与星图（Next.js + JSON）不直接复用代码。

**风险**
- 引入成本高：整套是微服务（多容器 + 向量库 + 队列），对「轻量 Next.js + JSON 文件存储」的星图是重量级依赖，收益/成本比低。
- 许可证：修改版 Apache 2.0，**禁止用其源码运营多租户 SaaS**，且**前端不可删除/修改 logo 与版权**——与星图「多用户 + 自有品牌」定位存在潜在冲突。
- 结论：**不引入**，抄思想。

#### 2. FastGPT — 知识库 + 可视化工作流 + Agent

- **仓库**：https://github.com/labring/FastGPT ｜ **Star** 29,495 ｜ **主语言** TypeScript（**Next.js**）｜ **许可证** 修改版 Apache 2.0（FastGPT Open Source License）｜ **归档** 否，`pushed_at` 2026-08-28
- **定位**：基于 LLM 的知识库平台，开箱即用的数据处理、RAG 检索、可视化 AI 工作流编排。**中文文档、中文友好**。

**核心机制 / 架构**
- 技术栈：**Next.js**（前后端一体）+ MongoDB（业务数据）+ PGVector / Milvus / zilliz（向量库）。与星图同属 Next.js 生态，是候选里技术栈最接近的平台。
- **知识库**：数据集 → 集合(collections) → 分块（自定义分块、文本预处理、**QA 拆分**）→ 向量化（Embedding）。支持文件夹/网页爬取/手动输入/CSV/**API 定时同步**。
- **Workflow**：可视化编排（基于 React Flow），节点含：用户问题引导、知识库检索、AI 对话(LLM)、问题分类、文本提取、HTTP 请求、变量更新、代码运行、指定回复、循环、判断器、**定时器（cron 触发）**、插件节点（HTTP/App 插件）。
- **Agent 模式**：基于 workflow 的高级编排，可多工具调用。
- 支持 **DeepSeek**（topics 标注 `deepseek`、`nextjs`、`mcp`）。

**与星图的关联点**
- 6:00 定时日报：**「定时器」节点可直接以 cron 触发 workflow**，是「定时任务 = 一种 workflow 触发器」思想的直接参照；且「知识库 API 定时同步」也示范了定时拉取外部数据的做法。
- 知识库分块/QA 拆分：若未来把「日记 + 对话沉淀」做成可检索记忆，其分块与 QA 拆分策略值得抄。
- 技术栈契合：同为 Next.js，读其 workflow 编辑器（React Flow）与定时器实现，学习成本最低。

**可借鉴资产**
- 「定时器作为 workflow 触发器」的建模方式（cron → 执行 DAG）。
- 知识库分块 + QA 拆分的具体策略（`projects/app` 内 knowledge 相关模块）。
- 技术栈：Next.js + React Flow + MongoDB/PGVector，与星图部分重叠。

**风险**
- 许可证同 Dify：**禁止多租户 SaaS**、**保留 logo**，与星图品牌冲突。
- 引入仍需 MongoDB + 向量库，非「JSON 文件存储」的轻量路线。
- 结论：**不引入**，抄「定时触发 workflow + 知识库分块」思想。

#### 3. LangGraph — 有状态多智能体编排

- **仓库**：https://github.com/langchain-ai/langgraph ｜ **Star** 40,647 ｜ **主语言** Python（另有 JS 版 `@langchain/langgraph`）｜ **许可证** MIT ｜ **归档** 否，`pushed_at` 2026-08-28
- **定位**：构建「可恢复(resilient)」智能体的底层库 —— 把 agent 建模为**有状态的图/状态机**，提供 checkpoint 持久化与断点续跑。

**核心机制 / 架构**
- **StateGraph**：节点(nodes，纯函数) + 边(edges，普通边 / 条件边 conditional edges)，共享一个 State（TypedDict / Pydantic 模型），数据沿边流动。
- **Checkpoint 持久化**：每个 super-step 自动保存状态快照(checkpoint)到 Checkpointer（MemorySaver / SqliteSaver / PostgresSaver / RedisSaver 等）；支持 `thread_id` 区分多会话，支持**时间旅行**（从任意 checkpoint 回放/分支）。
- **Durable execution**：断点续跑、节点重试、幂等执行——长任务/定时任务崩溃后可从中断处继续。
- **多智能体**：子图(subgraph)、`Send` API（map-reduce 扇出）、`Command`（handoff 交接）。
- 与 LangChain 松耦合，可独立使用。

**与星图的关联点**
- **自我进化提示词沉淀**：把「小星的一天」建模为 StateGraph 节点序列（读日记 → 读对话 → 算目标/自我/差距坐标 → 生成成长规划），每个节点后 checkpoint，天然支持"从某一步重跑/回放"，与星图 6:00 日报的「归纳→坐标→规划」流水线高度同构。
- 多技能路由：条件边(conditional edges) = 按状态路由到「测验/目标拆解/定位」不同技能节点，是最干净的「多技能路由」状态机范式。
- 6:00 定时日报：durable execution + checkpoint 是「定时任务幂等/断点续跑」的教科书实现思想。

**可借鉴资产**（抄思想）
- 「StateGraph + checkpoint + thread 会话」三件套的模式设计。
- 条件边做技能路由、checkpoint 做状态回放——可直接用轻量实现复刻到 Next.js（星图甚至可以用 JSON 文件当 checkpoint）。
- 技术栈：Python 为主；JS 版 `@langchain/langgraph` 存在但生态较薄，不推荐为此在 Next.js 里引 Python 运行时。

**风险**
- 引入 Python 运行时对纯 Next.js 项目是额外负担；JS 版成熟度与文档逊于 Python 版。
- 收益在「思想」而非「代码」，直接引入性价比低。
- 结论：**抄思想**（状态机 + checkpoint 持久化）。

#### 4. Eliza — 插件化多平台 AI 智能体框架

- **仓库**：https://github.com/elizaOS/eliza ｜ **Star** 19,202 ｜ **主语言** TypeScript ｜ **许可证** MIT ｜ **归档** 否，`pushed_at` 2026-08-29
- **定位**：开源的「智能体操作系统」，插件化接入多平台（Twitter/Discord/Telegram 等），TypeScript 单仓。

**核心机制 / 架构**
- 核心概念拆得很细（这是它最值得学的地方）：
  - **Character**：角色定义 JSON（`bio` 背景、`lore` 知识、`style` 风格、`messageExamples` 少样本、`plugins`、`clients`、`settings`）——人设与提示词全部声明式。
  - **Providers**：动态上下文注入（时间/钱包/新闻等），按周期刷新、带缓存（`cache architecture`），在每轮生成前把"当前状态"注入 prompt。
  - **Actions**：工具（`validate` / `handler` / `simulate`），注册后可被 function calling 触发。
  - **Evaluators**：每轮对话后运行，评估"是否满足条件 → 触发动作"，用于自我反思/状态迁移。
  - **Plugins**：打包 providers + actions + evaluators，实现能力隔离与复用；**Capability Router** 按能力把消息路由到远程插件（`capability-router-remote-plugins.md`）。
  - **Memories**：向量记忆 + RAG（sqlite + embedding）。
- **Agent Runtime**：消息处理管线（消息 → 路由 → 生成 → 动作执行），状态机驱动。

**与星图的关联点**
- **小星人设**：`Character` 的 bio/lore/style/messageExamples 结构，正是「小星」人生导师人设 + 自我进化提示词的理想数据模型（星图 JSON 存储可直接套此 schema）。
- **自我进化提示词注入**：`Providers` 的「每轮生成前注入当前上下文」机制，可直接映射为「把用户目标/坐标/日记摘要作为动态上下文注入小星 prompt」。
- **自我进化/反思**：`Evaluators` 的「每轮后评估 → 触发动作」对应星图「日报归纳 → 生成成长规划」的反思闭环。

**可借鉴资产**（抄思想 + 抄 schema）
- Character / Providers / Evaluators 三概念的 JSON schema 设计（TypeScript，MIT，可直接参考类型定义）。
- 「插件 = 能力隔离包」组织方式，可用于把「测验/目标拆解/定位」做成小星的三个能力模块。
- 技术栈：TypeScript 单仓，与星图同语言，但框架整体偏社交/加密平台（discord/twitter/crypto），带大量星图用不到的模块。

**风险**
- 框架庞大、依赖多（多客户端/加密相关），为「小星」单 agent 引入整套框架不划算。
- 社区更新快、API 变动频繁（open_issues 1388 较多）。
- 结论：**抄思想 + 抄 Character/Provider schema，不引入框架**。

**与星图的关联点**

- 小星多技能路由：其「Agent 市场 + 角色卡」与「多 agent 调度」是「一个产品里管理多个角色/技能」的产品形态参考。
- 技术栈：同为 Next.js，UI 组件思路可直接借鉴。

**可借鉴资产**（抄交互 + 抄组件思路）
- 对话流式渲染、发送卡片、Artifacts、插件市场等前端交互（Next.js + React）。

**风险**

- 项目已转向多智能体平台方向，作为「单一对话前端」引入会带入大量无关能力。

| 内心星图 3D 升级 | **react-force-graph-3d / 3d-force-graph**（快出效果）或 **@react-three/fiber + @react-three/drei**（深度定制） | MIT、纯前端 npm、依赖轻、与 Next.js/React 完全契合；一个组件替换手写 SVG 力模拟 | **P1 最高** |
| 星空氛围背景（可选） | **@tsparticles/react + preset-stars** | 一行组件、MIT、零后端 | P1（可选） |
| 6:00 定时日报（库层面） | **node-cron / croner**（+ 可选 **BullMQ + Redis** 做队列幂等） | 抄 n8n Schedule Trigger + Durable Scheduler 思想，用同栈轻量库自建，不引平台 | **P0 最高** |

### 🟡 抄思想（模式/数据结构值得学，代码不照搬）

| 目标 | 抄什么 | 来源 | 落地方式 |
|---|---|---|---|
| 小星多技能路由 | 「状态机 + 条件边」把测验/目标拆解/定位路由成技能节点 | LangGraph | 用轻量 TS 状态机（如 xstate 或自写 switch 状态图）实现 |
| 自我进化提示词沉淀 | 「Character(bio/lore/style/examples) + Providers(每轮注入当前上下文) + Evaluators(每轮后反思→动作)」 | Eliza | 直接套用其 JSON schema 存到星图 JSON 文件；把"目标/坐标/日记摘要"做成 Provider 注入 |
| 6:00 定时日报幂等 | 「cron 触发器 + 持久化调度队列 + 去重幂等 + 时区」 | n8n Durable Scheduler | node-cron/BullMQ + 幂等键（如"日期"去重） |
| 状态持久化/断点续跑 | 「checkpoint 快照 + thread 会话 + 时间旅行回放」 | LangGraph | 用 JSON 文件当 checkpoint，日报流水线每步落盘 |
| 对话前端交互 | 流式打字、发送卡片/快捷指令、语音、Artifacts、插件、主题 | LobeHub(原 Lobe Chat) | 抄交互设计，Next.js 自实现 |
| 知识库/长期记忆（未来） | 「分块 → 索引 → 检索 → rerank」三段式 RAG | Dify / FastGPT | 未来若给"小星"加记忆，照此拆模块 |
| 现 2.5D 继续优化 | d3-force 力参数（charge/linkDistance/collide/forceRadial 星座环） | d3 | 若暂不 3D，补力参数即可 |

### 🔴 不引入（作为平台/框架整仓引入，成本 > 收益）

| 项目 | 不引入的核心原因 |
|---|---|
| Dify / FastGPT | 微服务/向量库重依赖；许可证**禁多租户 SaaS + 保留 logo**，与星图多用户品牌定位冲突 |
| n8n / Activepieces | 为"一个 6:00 定时任务"引入整套工作流平台过重；fair-code / Enterprise License 非 OSI，许可语义复杂 |
| Open WebUI | Python + Svelte 栈不契合；Open WebUI License 带品牌条款 + CLA |
| Eliza | 框架庞大、偏社交/加密平台，为单 agent 引入整套依赖不划算（只抄其 schema） |
| LobeHub | 已转型多智能体平台 + 许可证改 Community License，不适合作单一对话前端整仓引入（只抄交互） |

> 一句话：**平台类（Dify/FastGPT/n8n/Open WebUI/Eliza/LobeHub）抄思想，不引入；可视化类（force-graph/R3F/drei/tsParticles）直接采用；定时任务用轻量库自建（抄 n8n 思想）。**
